# Принятые решения о методике и ограничениях проекта

## Назначение документа

- **Задача** — зафиксировать согласованные правила проектирования и пределы объёма.
- **Результат** — формулировки решений с указанием оснований.
- **Использование** — проверка рабочих материалов, моделей, испытаний и итоговой записки.
- **Признак готовности** — каждое внесённое решение подтверждается своим основанием.

| ID | Принятое решение | Основание |
| --- | --- | --- |
| DEC-003 | Для всей системы допускается не более пяти функциональных требований. Вербальное описание предметной области занимает не более трёх страниц в итоговой вёрстке. | Ограничения объёма проекта. Условие о числе функциональных требований пересмотрено решением DEC-021. |
| DEC-004 | FR ведутся отдельным списком в формате `FR-001`: Система **должна** … Критерии проверки ведутся в методике испытаний. Технические пункты задания проверяются отдельно. | Правила ведения требований и испытаний. |
| DEC-005 | Проект ведётся в согласованной последовательности из 11 этапов. Для концептуальной ER-модели применяется нотация Чена с легендой, для функциональной модели — IDEF0 с ICOM, для процессов — BPMN 2.0. При необходимости жизненный цикл описывается отдельно в UML State Machine. | Согласованная методика проектирования. |
| DEC-006 | Методическая строгость обязательна для рабочих материалов и итоговой записки. Существенные положения сопровождаются основаниями и статусами. Прослеживаемость проверяется от требования до испытания. Черновики согласуются явно. | Требования к методической строгости. |
| DEC-007 | Итоговый документ — единая индивидуальная пояснительная записка по ГОСТ 7.32-2017. Согласованные FR и определения переносятся дословно. Шпаргалка по проектированию и личный план изучения ведутся отдельно. | Правила подготовки итогового комплекта. |
| DEC-008 | Ориентир ТЗ для основного текста — до 20 страниц. Превышение этого объёма допускается ради сохранения согласованных формулировок. Трёхстраничный предел вербального описания обязателен. | Правила подготовки итогового комплекта. |
| DEC-009 | Работа ведётся по согласованным этапам. Отклонение от последовательности допускается только по отдельному явному согласованию. | Установленный порядок перехода между этапами. |
| DEC-010 | Для новой темы выбирается прикладная область вне образования с содержательной ролью ИИ в основном процессе. | Критерии отбора новой предметной области. Часть о применении ИИ заменена решением DEC-012. |
| DEC-011 | Контекст принятых решений ведётся отдельно от материалов для защиты. Итоговые файлы оформляются как самостоятельные артефакты проекта. Для проектных документов применяются безличные формулировки. | Правила оформления рабочего и итогового комплектов. |
| DEC-012 | Выбирается компактная прикладная область с одним сквозным процессом и минимальным числом ролей. Применение ИИ исключено из базового объёма. | Уточнение границ проекта. Заменяет DEC-010 в части применения ИИ. |
| DEC-017 | При обсуждении требования в рабочем чате приводится его полная формулировка. Указываются идентификатор, если он присвоен, и статус формулировки. | Порядок согласования требований. |
| DEC-020 | В проектной документации и рабочем обсуждении применяется строгий академический стиль. Существенные термины определяются, сокращения расшифровываются при первом употреблении. | Правила академического изложения. |
| DEC-021 | Рекомендуемый объём — не более пяти функциональных требований. При необходимости число требований может превышать этот ориентир. Предел в три страницы для вербального описания сохраняется. | Пересмотр DEC-003 в части числа функциональных требований. |
| DEC-022 | Предварительные формулировки функциональных требований подготавливаются до завершения согласования замысла и границ. Систематизация перечня сохраняется в установленном порядке этапов. | Согласованное отклонение от последовательности работ. |
| DEC-035 | Процессы проверяются сквозным образом от исходных условий до результата с учётом отказов, источников данных и границ ответственности. | Правило проверки полноты сценариев. |
| DEC-047 | Диаграммы в Miro создаются из редактируемых фигур, подписей и соединителей. | Правило подготовки рабочих моделей для совместного редактирования. |
| DEC-048 | Для каждого процесса и подпроцесса явно определяются событие запуска, предусловия, обязательные начальные входные данные, их источники и исход при отсутствии либо недействительности обязательного входа. | Уточнение правила сквозной проверки DEC-035. |
| DEC-051 | Для каждого действия приложения, которое читает или изменяет данные, на процессной диаграмме показывается конкретный источник или получатель данных и направление обращения. | Уточнение правил процессного моделирования DEC-035 и DEC-048. |
