# 07. Архитектура системы

**Статус — рабочая редакция шага 07.3.**

## Назначение документа

- **Задача** — распределить ответственность между компонентами.
- **Результат** — три архитектурных представления C4, сопоставление с функциями и описание логических интерфейсов.
- **Использование** — подготовка технического проекта.
- **Признак готовности** — для каждой функции указан ответственный компонент, связи и интерфейсы объяснены.

## Границы системы

Для проектируемой системы предлагается веб-приложение с личным кабинетом, единым серверным приложением и базой данных PostgreSQL. Серверное приложение разделяется на модули по предметной ответственности и развёртывается как единый компонент. Внешние сервисы регистрации, проверки документов и оплаты взаимодействуют с серверным приложением через отдельные интерфейсы. Для отправки маршрутной квитанции предусматривается интерфейс почтовой доставки.

Личный кабинет передаёт команды владельца аккаунта и отображает результаты. Серверное приложение проверяет доступ, применяет предметные правила, связывает ответы внешних сервисов с локальными операциями и изменяет состояние данных. База данных обеспечивает устойчивое хранение записей, ограничения целостности и атомарность связанных изменений.

## Компоненты и ответственность

Коды A1–A5 соответствуют узлам [функциональной модели](../models/05-functional-model.md).

| Компонент или модуль | Функция | Ответственность |
| --- | --- | --- |
| Личный кабинет | A1–A5, пользовательское взаимодействие | Формы регистрации и входа, выбор рейса и пассажира, управление бронированиями и представление результатов. |
| Аккаунты и доступ | A1 | Запрашивает регистрацию, создаёт связанный аккаунт после подтверждения, устанавливает наличие аккаунта по данным PostgreSQL, проверяет учётные данные при входе и определяет контекст аккаунта для последующих операций. |
| Пассажиры и документы | A2 | Ведёт записи о пассажирах и документах, принимает файлы в личном кабинете, направляет документы на внешнюю проверку и сохраняет результат для конкретного документа. Передаёт модулю бронирования сведения для проверки допуска. |
| Рейсы и бронирования | A3, A5 | Предоставляет сведения о рейсах и доступности мест. Оформляет бронирование, ведёт его состояние и закрепления. Проверяет пределы пассажирской и багажной вместимости, выполняет смену места на том же рейсе, добавление багажа и отмену. Проверяет наличие основания для подачи запроса на возврат. |
| Платежи и билеты | A4 | Инициирует оплату и доплату, учитывает результаты платёжных попыток, оформляет билет после подтверждения оплаты. Направляет запросы на возврат и учитывает переданные платёжным сервисом состояния. |
| Представление поездки | A5 | Предоставляет список и сведения о бронированиях данного аккаунта, включая последнее известное состояние запроса на возврат при его наличии. Формирует маршрутную квитанцию по данным оформленного билета, предоставляет её для просмотра и печати, передаёт её на почтовую доставку при соответствующем запросе. |
| База данных PostgreSQL | A1–A5, хранение и целостность | Хранит учётные записи приложения, предметные записи и состояния операций. Обеспечивает ограничения и транзакции, необходимые для согласованного изменения связанных данных. |

Модуль «Рейсы и бронирования» отвечает за состояние бронирования и закреплений, а модуль «Платежи и билеты» отвечает за платёжные попытки, билеты и состояния запросов на возврат. Согласованные изменения нескольких записей после обработки результата платежа выполняются в одной локальной транзакции. Вызов внешнего сервиса и получение его ответа выполняются за границами этой транзакции.

## Внешние участники и исходные данные

| Источник | Данные или результат | Получатель и назначение |
| --- | --- | --- |
| Владелец аккаунта через личный кабинет | Учётные данные, сведения о пассажире и документе, файл документа, параметры бронирования и команды обслуживания. | Серверное приложение проверяет состав и принадлежность данных операции. |
| Сервис регистрации | Подтверждение регистрации и сведения для связывания учётной записи с аккаунтом. | Модуль «Аккаунты и доступ» создаёт связанный аккаунт. Проверка при последующем входе выполняется приложением. |
| Внешний сервис проверки документов | Результат проверки документа, загруженного после входа. | Модуль «Пассажиры и документы» связывает результат с документом. Модуль «Рейсы и бронирования» использует сохранённый результат при проверке допуска пассажира. |
| Внешний платёжный сервис | Результаты оплаты и доплаты, состояния и итог запроса на возврат. | Модуль «Платежи и билеты» сопоставляет ответ с платёжной попыткой или запросом на возврат и передаёт сведения для обновления связанных записей. |
| Исходный набор сведений о рейсах | Расписание, аэропорты, пассажирские места, багажная вместимость и цены. | Рабочее допущение для проектирования — исходные сведения поступают в базу данных через пакетную загрузку с проверкой. Каталог и доступность формируются по загруженным сведениям и действующим закреплениям. |

Почтовой доставке передаётся сформированная маршрутная квитанция и адрес назначения. Данные для составления квитанции поступают из учёта оформленных билетов и связанных с ними сведений о бронировании, рейсе и пассажире.

## Архитектурные представления C4

Уровни отражают разные масштабы одной системы. Контекст показывает владельца аккаунта и внешние программные системы. Контейнеры показывают выполняемые части приложения и хранилище. Компонентное представление раскрывает внутреннее устройство серверного приложения. Методическое основание — описания [контекста системы](https://c4model.com/diagrams/system-context), [контейнеров](https://c4model.com/diagrams/container) и [компонентов](https://c4model.com/diagrams/component) модели C4.

| Уровень | Содержание | Диаграммы |
| --- | --- | --- |
| 1. Контекст системы | Система, владелец аккаунта, сервисы регистрации, проверки документов, оплаты и почтовой доставки. Общая функция соответствует узлу A0 IDEF0. | [SVG](07-c4-context.svg), [Miro](https://miro.com/app/board/uXjVEQ80zpk=/?moveToWidget=3458764689957186978) |
| 2. Контейнеры | Личный кабинет, единое серверное приложение и PostgreSQL. Личный кабинет принимает команды и отображает результаты, сервер выполняет A1–A5, PostgreSQL хранит данные и обеспечивает целостность. | [SVG](07-c4-containers.svg), [Miro](https://miro.com/app/board/uXjVEQ80zpk=/?moveToWidget=3458764689957186979) |
| 3. Компоненты сервера | Предметные модули с привязкой к A1–A5, обработка веб-запросов, доступ к данным и пакетная загрузка каталога. | [SVG](07-c4-components.svg), [Miro](https://miro.com/app/board/uXjVEQ80zpk=/?moveToWidget=3458764689957186980) |

Личный кабинет представлен как клиентский веб-контейнер в браузере. Это рабочее архитектурное решение. Серверные компоненты входят в один контейнер и развёртываются вместе. Оплата и доплата выполняются на форме внешнего платёжного сервиса. Набор сведений о рейсах представлен как исходные данные пакетной загрузки. Уровень кода относится к последующей технической детализации.

### Связь с функциями системы

Сопоставление использует коды [функциональной модели IDEF0](../models/05-functional-model.md) и [процессной модели](../models/06-process-model.md). На диаграммах Miro коды A открывают соответствующие узлы IDEF0.

| Функция | Ответственный компонент C4 | Выполняемая операция и связанный сценарий | Интерфейсы |
| --- | --- | --- | --- |
| A1. Обеспечить регистрацию и доступ | Аккаунты и доступ | Сопоставляет результат регистрации с запросом и создаёт связанный аккаунт. При входе проверяет наличие аккаунта и учётные данные, затем устанавливает контекст доступа. P01. | IF-01, IF-02, IF-07 |
| A2. Вести сведения о пассажирах и организовать проверку документов | Пассажиры и документы | Ведёт список пассажиров. Принимает документ после входа, направляет его на внешнюю проверку и сохраняет результат по конкретному документу. Передаёт сведения для проверки допуска. P01, P02. | IF-01, IF-03, IF-07 |
| A3. Предоставить сведения о рейсах и оформить бронирование | Рейсы и бронирования | Выдаёт сведения о рейсах и местах, проверяет допуск и оба предела вместимости, создаёт бронирование и временные закрепления. Пакетная загрузка подготавливает каталог. P02. | IF-01, IF-06, IF-07 |
| A4. Обработать платёжные операции и оформить билет | Платежи и билеты | Инициирует оплату, доплату и обработку возврата, сопоставляет результат с операцией, оформляет билет после подтверждения основной оплаты. Передаёт результат для изменения брони или закреплений. P02–P04. | IF-01, IF-04, IF-07 |
| A5. Обслужить оформленное бронирование | Рейсы и бронирования, Представление поездки | Первый компонент меняет место, учитывает багаж, оформляет отмену и проверяет основания возврата. Второй предоставляет сведения, квитанцию и состояние возврата. Платёжные операции выполняет компонент A4. P03, P04. | IF-01, IF-04, IF-05, IF-07 |

Компонент обработки веб-запросов определяет контекст аккаунта и направляет операции предметным модулям. Компонент доступа к данным обеспечивает единый доступ к PostgreSQL и участие предметных изменений в локальных транзакциях. Вызовы внешних сервисов выполняются за границами этих транзакций.

## Схема компонентов и интерфейсов

[Схема компонентов и интерфейсов](07-system-architecture.svg). [Редактируемая схема в Miro](https://miro.com/app/board/uXjVEQ80zpk=/?moveToWidget=3458764689781037179).

Коды IF обозначают архитектурные интерфейсы. Состав данных приведён на логическом уровне и сопоставлен с [начальными входными данными процессов](../models/06-process-model.md#начальные-входные-данные-процессов). Идентификаторы операций формирует соответствующий серверный модуль. Входящие сообщения внешних сервисов проверяются и сопоставляются с операцией до изменения состояния. Повторная обработка уже принятого результата не создаёт второй билет, повторное закрепление или второй переход состояния.

| Код | Инициатор и получатель | Входные данные и источник | Результат и обработка отказа |
| --- | --- | --- | --- |
| IF-01 | Владелец и личный кабинет → серверное приложение | Команда, обязательные параметры операции и контекст аккаунта для защищённых действий. Параметры поступают из формы или выбора владельца, контекст формирует сервер после входа. Состав входа указан по операциям P01–P04. | Сервер определяет контекст аккаунта и передаёт команду ответственному модулю. Личный кабинет получает данные, состояние или причину отказа. При недействительном входе операция прекращается до предметных изменений. |
| IF-02 | Модуль «Аккаунты и доступ» ↔ сервис регистрации | Сведения формы и признак связи с локальным запросом. Сервис возвращает результат и идентификатор зарегистрированной учётной записи при успехе. | Связанный аккаунт создаётся после подтверждения и сопоставления результата с запросом. При неполном или несопоставимом ответе аккаунт не создаётся. |
| IF-03 | Модуль «Пассажиры и документы» ↔ внешний сервис проверки документов | Файл и реквизиты проверяемого документа из личного кабинета, идентификатор проверки от приложения. Сервис возвращает идентификатор или согласованный признак сопоставления и результат. | Приложение направляет документ после проверки доступа и комплектности. Ответ применяется к связанной записи проверки. Несопоставимое сообщение не изменяет состояние проверки. |
| IF-04 | Модуль «Платежи и билеты» ↔ внешний платёжный сервис | Для оплаты и доплаты передаются идентификатор попытки, сумма и валюта из учёта приложения. Для возврата передаются идентификатор запроса, ссылка на подтверждённую оплату и сумма в валюте этой оплаты, если сумма уже определена. Сервис возвращает ссылку для оплаты, состояния и итоговые результаты. | Форма оплаты открывается на стороне платёжного сервиса. При подтверждении оплаты или доплаты сверяются сумма и валюта с данными платёжной попытки. Сопоставленный и проверенный итог применяется однократно. При неопределённом результате закрепления сохраняются. Фактическое перечисление при возврате выполняет платёжный сервис. |
| IF-05 | Модуль «Представление поездки» → почтовая доставка | Адрес назначения, указанный для отправки, и маршрутная квитанция, сформированная приложением по оформленному билету. | Интерфейс возвращает результат приёма к отправке. При некорректном адресе запрос не передаётся. Ошибка доставки отражается в результате операции отправки. |
| IF-06 | Исходный набор сведений → пакетная загрузка | Файл со сведениями о расписании, аэропортах, местах, вместимости и ценах. Источник — подготовленный набор исходных данных. | Модуль пакетной загрузки проверяет комплектность и согласованность сведений перед записью. Некорректные данные отклоняются с указанием причины. Формат и правила частичной загрузки определяются на техническом этапе. |
| IF-07 | Серверное приложение ↔ PostgreSQL | Параметры чтения и команды изменения от серверных модулей, включая идентификаторы, состояния и данные для проверки предметных ограничений. | База данных возвращает записи или результат операции. При нарушении ограничения либо сбое незавершённая транзакция откатывается. Приложение обрабатывает отказ и формирует наблюдаемый исход. |

На архитектурной схеме стрелки показывают направление передачи данных. Двусторонние стрелки обозначают обмен запросами и ответами или результатами. Сообщения о проверке, оплате и возврате могут поступать после исходного запроса. Конкретный способ их доставки определяется при выборе внешнего сервиса.

## Основания архитектурных решений

Единое серверное приложение предложено с учётом объёма системы и необходимости согласованно изменять данные о бронировании, платеже, билете и закреплениях. Выделение модулей задаёт предметную ответственность в пределах одного приложения. Конкретные поставщики интеграций, способ подготовки учётных данных для последующего входа, место хранения загруженных файлов и транспортные форматы относятся к последующей детализации контрактов.
